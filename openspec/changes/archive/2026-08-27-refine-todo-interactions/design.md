# Design: refine-todo-interactions

## Context

Todo v0.1 的前端把每张任务卡片实现为常驻展开的表单（`TaskCard.tsx`），所有变更经由 `mutate() → refresh()` 全量重拉 `/api/todo` 的 projects + tasks + 当前视图，期间用全局 `mutating` 标志禁用页面上全部输入。Projects 页的项目简介和"已完成事项"另有独立的暂存草稿与整包保存按钮，会被任何触发的刷新覆盖。

后端已经提供所需的全部能力：单任务 PATCH、`planned_date` 独立可写、项目 PATCH 支持整组 `completed_items`。因此本次变更完全落在前端交互层，不触碰模块边界、API 契约和领域语义。

## Goals / Non-Goals

**Goals:**

- 让"看清单"和"改任务"两种动作分离：默认紧凑行保证扫视效率，展开面板承载编辑。
- 全模块统一为一种提交心智："离开字段或改变选项 = 已保存"，不再出现第二套保存规则。
- 把 Carryover → Today 这条每天走的高频路径压缩到一次点击。
- 变更反馈即时化：界面先动，请求在后；失败可见且可回退；输入永不被后台数据冲掉。

**Non-Goals:**

- 不新增后端批量端点：Carryover 批量挪期用现有逐条 PATCH 顺序执行（个人规模下任务是几十条以内）。
- 不做拖拽排序、搜索/过滤、跨视图批量选择（用户未选中该痛点）。
- 不动 AI proposal 流程（逐条接受/拒绝被明确排除在本次范围外）。
- 不给 `doing` 状态加界面入口（同上，属于另一个未被选中的问题）。
- 不改 Today 查询的只读语义：查询继续原样报告 Carryover，挪期必须是用户显式发起的任务更新。

## Decisions

### 1. 卡片默认收起，点开才编辑

收起态渲染一行：完成勾选框、标题文本、以及少量元信息徽标（所属项目、Next Action 星标、计划/截止日期、优先级点、有无备注图标）。点击行体切换到展开态，才渲染标题输入、备注 textarea、项目/计划/截止/优先级控件和 Cancel / Make next / Delete 操作。

理由：现有布局把"查看"和"编辑"混在同一表单里，信息密度和误触率同时升高。列表的主要用途是扫视和勾选，重编辑是低频分支操作。展开状态保存在组件本地，key 用任务 id 保持稳定，后台对账替换数据时不会导致折叠状态闪烁。

### 2. 统一"离开即提交"，删除每卡 Save 按钮

规则收敛为一条：字段落焦离开（blur）或下拉/日期改变选项时立即 PATCH；标题输入额外支持回车提交。取消 Save 按钮。

理由：现状里下拉和日期是"改变即生效"、标题却要找按钮确认，两套规则并存是"不确定有没有保存上"的直接来源。单一规则之下没有需要记忆的例外。取消部分字段的下拉仍然立即生效——这条不变，只是把其余字段对齐到它。

### 3. 乐观更新替代全页刷新 + 全局锁

`mutate()` 重构为定向更新：PATCH 先应用到本地状态（打勾立刻变实心、日期立刻变化），请求成功后由响应值校正该条记录，随后进行一次无 loading 态的静默对账让 Today 分组等派生视图回到服务端口径。失败时回滚该条之前的快照并就地显示错误行内提示。`mutating` 全局标志移除，pending 态只出现在发起请求的那个控件上；整页 loading 只保留在首屏和切换视图时。

理由：个人单机应用里每次小改动都付一次全量 RTT 是顿挫感的根源。静默对账保留了服务端定义的视图分组逻辑（Today/Carryover 按本地日期划分），避免在前端复刻时区与分组规则。

### 4. 对账永不写回正在编辑中的控件

任何后台数据到达时，如果某个输入控件当前处于聚焦/未提交状态，跳过向该控件回写服务器值；失焦提交发生后恢复正常对账。任务卡片的标题/备注与 Projects 页的项目简介 textarea 均适用同一条机制。

理由：这是"输入中被冲掉"一类问题的通用解法，比给简介草稿单独做 dirty 跟踪更简单，而且顺带修复了任务卡片上同类但更隐蔽的状态复位。

### 5. 项目简介与已完成事项并入统一提交模型

移除"先逐条加入本地列表、再点保存按钮整包提交"的两段式：已完成事项每添加/删除一条就单独 PATCH 项目（整体数组替换是 API 现有语义，单用户场景安全）；简介在 blur 时提交。配套移除该区域独立的保存按钮并更新文案说明。

备选方案是保留显式保存按钮仅增加 dirty 保护；弃用原因是它维持了"这里还有一个独立保存模型"的心智负担，而这正是被抱怨的问题之一。

### 6. 挪期快捷动作：单行 + 区块批量两级

Carryover 与 Upcoming 行在收起态直接提供"→ 今天"快捷钮；Carryover 区块标题旁提供"全部移到今天"。两者都是显式的单任务 PATCH（批量=顺序多条 PATCH + 乐观 UI），Today 分组随之通过静默对账刷新。批量过程中的单条失败不影响已成功的其他条目，失败的条目回滚自身并单独提示。

理由：现状要求逐个打开日期选择器，而"重新安排今天"是本模块的核心循环。保持查询端只读、把改动表达为普通任务更新，避免违反既有 spec 中"Carryover 查询不改写 planned_date"的边界。

## Risks / Trade-offs

- [乐观更新与静默对账并存] 需要仔细处理竞态（请求返回顺序）。 → 用版本号或请求序号只接受最新一次对账结果；单元路径虽无自动化覆盖，但在 tasks.md 走查清单中列为必验项。
- [blur 提交长文本] 用户可能意外点击别处导致半句描述被保存。 → 可接受：内容仍完整留在输入框中可继续修改；相比数据丢失风险这一取舍成本更低。
- [批量挪期为 N 次 HTTP] 大列表时请求多。 → 个人规模下不构成瓶颈；如未来需要再演进为专用批量端点（届时走 Modified Capabilities）。

## Migration Plan

纯前端变更，无数据迁移。合并后用户手动重启 Vite 开发服务即可生效。
