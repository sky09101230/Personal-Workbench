# Proposal: refine-todo-interactions

## Why

Todo 模块的功能骨架已经可用，但日常使用的操作路径偏重，用户的直接反馈是"用着不顺手"。把体感拆开定位后确认五个交互问题：

1. 任务卡片是常驻展开的重表单（备注框 + 四个字段控件 + 一排按钮），扫一眼列表的代价太高。
2. 保存规则不一致：改优先级/日期立即生效，改标题却要点 Save 按钮，用户无法确定何时算保存。
3. 把昨天没做完的任务挪进 Today 只能逐个打开日期选择器手工挑选，而"重新安排今天"恰恰是这个模块每天的核心动作。
4. 每次小改动都触发全页重拉数据并锁定所有输入框，连续操作有明显顿挫感。
5. Projects 页的项目简介与"已完成事项"是本地暂存草稿，任何其他操作触发的刷新都会覆盖未保存的内容。

这五条都发生在前端交互层；现有领域模型、API 契约和后端服务已经支持所需的全部能力，无需后端改动。

## What Changes

- 任务卡片改为"默认收起的紧凑行 + 点开展开的编辑面板"：收起时显示勾选框、标题和关键元信息（项目、Next Action、计划/截止日期、优先级、有无备注），展开后才出现编辑字段。
- 统一提交语义：所有任务字段在"离开字段或改变选项"时立即持久化，标题回车即提交；取消每张卡片的 Save 按钮。项目简介与已完成事项并入同一模型——简介失焦保存，已完成事项逐条增删即时持久化，移除暂存加整包保存的两段式流程。
- Carryover 行提供单任务"移到今天"，Carryover 区块提供批量"全部移到今天"；Upcoming 行同样提供单个"排到今天"。全部通过现有的单任务 PATCH 实现，不新增批量端点。
- 变更为乐观更新：改动先落到界面再发请求，失败时回滚并就地报错；请求期间只禁用当前正在操作的控件，不再锁整页；后台静默对账负责让派生视图回到服务端口径。
- 对账数据永不写回用户正在编辑中的控件，消除"输入中被刷新冲掉"这一类问题。

明确不变的部分：Today 查询仍只读报告 Carryover、不改写 `planned_date`（挪期由用户显式发起的单任务更新完成）；AI proposal 的生成/Accept/Reject 流程不动；`doing` 状态入口、搜索过滤、手动拖拽排序不在本次范围内。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `todo-project-task-management`: 新增紧凑卡片布局、字段级提交语义、项目简介与已完成事项安全编辑的需求；现有生命周期、Next Action、API 契约需求保持不变。
- `todo-today-views`: 新增一次性挪期操作与乐观更新反馈的需求；Carryover 查询只读边界、五个核心视图结构保持不变。

## Impact

- 前端：仅 `apps/web/src/modules/todo/` —— `TodoPage.tsx`（数据流与变更处理重构）、`components/TaskCard.tsx`（收起/展开双态）、`todo.css`（紧凑行样式），`types.ts`/`api.ts` 不变。
- 后端：无改动。`apps/api/app/modules/todo/**` 全部不动；pytest 套件应保持全绿作为回归证据。
- 数据库与配置：无 schema 或环境变量变化。
- 验证方式：前端生产构建 + 后端 pytest 回归 + OpenSpec strict 校验；浏览器行为目前没有自动化测试，实现完成后需按 tasks.md 的清单人工走查每个场景。
